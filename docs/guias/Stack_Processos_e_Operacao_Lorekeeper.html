Stack e processos do Lorekeeper

As decisões e os procedimentos necessários para chegar à aplicação atual, sem reproduzir tentativas de retrabalho. Inclui arquitetura, setup, integração automática, testes, rede privada, backup e problemas que tiveram solução definida.

Base: repositório GitHub main no commit bac4624, especificações, PRs e resultados do Codex compartilhados até 23/11/2026. Não houve acesso direto à sessão do Codex nesta consulta.

1. Arquitetura

Aplicação web monolítica para uso pessoal. O Node/Fastify hospeda uma API e os arquivos da interface React; o SQLite persiste campanhas, sessões, documentos, relações, revisões, tags e dados de busca. Os dispositivos acessam uma única instância.

O navegador mantém rascunhos pendentes localmente; a última gravação confirmada é centralizada no servidor. Não existem contas públicas, colaboração, sincronização entre bases SQLite distintas nem uma camada de IA obrigatória.

4. GitHub, Ruleset e GitHub App

  1. Repositório e CI: repositório público de uso pessoal, branch padrão main, Actions habilitado e opção Allow auto-merge ativa.
  2. Ruleset da main: Active, branch alvo main, Pull Request obrigatório, 0 aprovações humanas obrigatórias, check validar da integração GitHub Actions, base atualizada, bypass vazio, restrições a deleções/force push.
  3. GitHub App: instalada somente no Lorekeeper, com leitura de metadados e escrita de Contents/Pull Requests. Chave privada em .pem gerada nas configurações da App, sem versioná-la.
  4. Variável e secret corretos: vars.LOREKEEPER_APP_CLIENT_ID em Repository variables; secrets.LOREKEEPER_APP_PRIVATE_KEY em Repository secrets. Não inverter.
  5. Três componentes: ci.yml define o job validar; notify-codex-branch.yml apenas sinaliza eventos, sem checkout nem secrets; github-app.yml executa código confiável da main com token temporário da App.
  6. Integração protegida: branches internas codex/, feat/, fix/, chore/ e docs/, autor aprovado e PR sem conflito. O bot solicita auto-merge pendente do CI ou reconcilia depois do check, sempre sujeito ao Ruleset.

Forks, autores desconhecidos, mudanças em raízes de confiança do CI, arquivos de credenciais ou SQL destrutivo não entram no fluxo automático comum. Migrações elegíveis devem ter testes de integridade, preservação e rollback. A reconciliação também roda periodicamente, a cada 15 minutos.

Marco validado: no PR #7, a identidade lorekeeper-pr-bot[bot] abriu PR, solicitou auto-merge, aguardou validar e integrou à main sem intervenção humana. A política foi depois ampliada pelo PR #20.

5. SDD, TDD e CI

SDD

Funcionalidade descrita em docs/specs/; critérios rastreados até MVP.md; caminhos de erro e preservação de dados definidos antes da implementação.

TDD

Red → Green → Refactor. Teste falha pelo comportamento ausente, implementação mínima, refatoração e regressão. Não confundir falha de instalação com evidência Red.

npm ci --include=dev
npm run lint
npm run typecheck
npm run test:unit
npm run test:integration
npm run build
npx playwright install chromium
npm run test:e2e

O CI executa essas verificações em Ubuntu 24.04 com check obrigatório validar. Em falha E2E, publica playwright-failures, incluindo trace e contexto de erro (retenção configurada: 7 dias). O merge só é autorizado para o candidato correto; o CI também roda após o merge na main.

6. Instalação e execução no Windows

  1. Instalar Git ou GitHub Desktop e clonar o repositório; usar main → Fetch origin → Pull origin para atualizar.
  2. Instalar Node 24.22.3 e npm 11.19.1, conforme .nvmrc/package.json.
  3. Se o driver SQLite necessitar compilar, instalar Visual Studio Community ou Build Tools com Desktop development with C++, MSVC e Windows SDK.
  4. Instalar, compilar e iniciar pelo PowerShell. Abrir a aplicação com o servidor em execução.
node --version
npm.cmd --version
npm.cmd ci --include=dev
npm.cmd run build
npm.cmd start
# http://127.0.0.1:3000

npm.cmd contorna a restrição do npm.ps1 no Windows PowerShell; alternativamente pode-se configurar RemoteSigned somente para o usuário. Para testes manuais e migrações, use um banco independente com LOREKEEPER_DB_PATH e escolha a porta via PORT.

$env:LOREKEEPER_DB_PATH = "$env:LOCALAPPDATA\Lorekeeper-Piloto\operacao-i4\piloto.sqlite"
$env:PORT = "3000"
npm.cmd start

7. Acesso privado entre dispositivos

No host Windows, a aplicação permanece restrita a 127.0.0.1. O Tailscale cria a rede privada; com MagicDNS e certificados HTTPS habilitados, Tailscale Serve encaminha a URL privada ao servidor local. Não usar Funnel nem expor a porta ao roteador.

tailscale status
tailscale serve --bg http://127.0.0.1:3000
tailscale serve status
# Encerrar o serviço privado:
tailscale serve --https=443 off

O ensaio I2-07 no Windows confirmou 4/4 cenários: acesso/gravação por HTTPS, sincronização de dois dispositivos autorizados, bloqueio externo e isolamento direto da API. Uma implantação Linux futura ainda precisará validar suas próprias permissões, serviço e configuração de rede.

8. Exportação, backups e piloto operacional

Exportação: o painel disponibiliza ZIP com lorekeeper.json versionado e Markdown por documento. Backup operacional: a CLI produz cópia SQLite consistente, validada quanto à integridade, e arquivos externos .lkb criptografados com AES-256-GCM e chave binária de 32 bytes.

# Copiar e restaurar em arquivos separados
node src/server/backup-cli.ts backup data/lorekeeper.sqlite backups/copia.sqlite
node src/server/backup-cli.ts restore backups/copia.sqlite ensaio/restaurado.sqlite

# Backup externo criptografado (exemplos de caminhos)
node src/server/backup-cli.ts encrypt data/lorekeeper.sqlite E:\Lorekeeper\Backups\copia.lkb C:\diretorio-privado\backup-i4.bin
node src/server/backup-cli.ts decrypt E:\Lorekeeper\Backups\copia.lkb ensaio\restaurado.sqlite C:\diretorio-privado\backup-i4.bin

O projeto determina chave separada do volume de backup, confirmação de destino real, logs privados, retenção de sete cópias diárias e quatro semanais, ausência de sobrescrita e teste de recuperação em outra instância. O diretório temporário do processo deve ser privado: uma interrupção abrupta pode deixar vestígios de backup em claro nesse volume.

10. Problemáticas e caminhos adotados

ProblemaDiagnóstico e solução definitiva
HTTP 403 no Codex CloudA API e os redirecionamentos de artefatos tinham permissões/restrições próprias do Cloud. Não indicavam falha do GitHub PR Bot. A App passou a abrir e integrar PRs; os logs e artefatos podem ser consultados por conexão GitHub autorizada.
Merge automático bloqueadoEscopo inicial de branch/diff e verificação redundante do Ruleset. Corrigido usando proteção nativa, autorização restrita e reconciliação após CI.
npm.ps1 bloqueadoPolítica PowerShell; usar npm.cmd ou RemoteSigned apenas em CurrentUser.
Falha node-gyp em better-sqlite3Ausência de toolset MSVC/C++; instalar Desktop development with C++, Windows SDK e compilar novamente.
ERR_CONNECTION_REFUSEDServidor local não estava respondendo na porta; executar/reiniciar npm start e conferir a URL.
Timeout de testes após assertionsFastify aguardava sockets keep-alive durante a limpeza. Padronizado fechamento dos clientes e contextos antes do servidor e drenagem de conexões ociosas; preservar traces.
Script da chave no PowerShell 5.1Assinaturas modernas do .NET incompatíveis; usar RNG, escrita de byte[] e limpeza compatíveis com .NET Framework, sem revelar segredo.
Backup sem unidade ou chave recuperávelValidar identificador do volume, não redirecionar para disco interno, guardar chave em cofre separado e testar recuperação antes de confiar no agendamento.

11. Checklist de operação e pendências

  1. Continuar implementando novos critérios com SDD, Red → Green → Refactor e CI obrigatório.
  2. Confirmar merge e CI de main antes de etapas dependentes; não enfraquecer o Ruleset para contornar falhas.
  3. Após a primeira execução agendada do backup, conferir arquivo, log, integridade e unidade de destino real.
  4. Restaurar um .lkb para outro arquivo SQLite, iniciar instância isolada em outra porta e medir o tempo até consultar uma sessão pela busca.
  5. Testar criação, edição e pesquisa no MVP atual entre dois dispositivos autorizados.
  6. Registrar os resultados reais no roteiro I4-04 e no roadmap. Só então marcar o piloto e o MVP operacional como concluídos.

Depois do MVP, o roadmap aponta PWA/offline, organização narrativa e linha do tempo, facções/itens, importação de arquivos, referências de regras, grafo e IA opcional com fontes verificáveis.
